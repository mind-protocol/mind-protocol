# CONCEPT: Space Encryption — At-Rest Encryption of Non-Public Graph Content

```
STATUS: DESIGNING
CREATED: 2026-03-13
```

---

## WHAT IT IS

At-rest encryption of non-public content within the Mind Protocol universe graph.

Every universe is a single FalkorDB graph. That graph contains everything: public piazzas, private minds, guild halls, Telegram chats, repositories, memories. All of it — one graph, one database. Space Encryption ensures that when content is private, it is unreadable without the correct keys, even if the entire database is exfiltrated.

The mechanism is hybrid cryptography applied to the graph structure itself:
- Each private Space has a **symmetric key** (AES-256) that encrypts its content
- Each Actor has an **asymmetric key pair** (public/private) that wraps Space keys
- The encrypted Space key lives on the **HAS_ACCESS link** between Actor and Space
- To read: decrypt the Space key with your private key, then decrypt the content

This is not access control. Access control determines who may request content. Space Encryption determines who can **read** content — even with full database access.

---

## WHY IT EXISTS

One graph per universe is the right architectural decision. It eliminates cross-database joins, enables physics to propagate across all Spaces, and keeps the schema unified. But it creates a single point of catastrophic breach: compromise the database, compromise everything.

Space Encryption neutralizes that risk. A compromised graph reveals **topology** — who is connected to whom, which Spaces exist, energy flows, trust weights — but not **content**. The attacker sees the shape of the world but cannot read any private conversation, memory, or synthesis.

Without this:
- A database breach exposes every citizen's private mind, every private conversation, every guild secret
- Hosting providers can read all content at rest
- Internal tooling with database access has implicit read access to everything
- There is no meaningful privacy — only the illusion of it via application-layer access control

---

## KEY PROPERTIES

- **Symmetric per Space:** Each private Space gets one AES-256 key. All content within that Space (Moments, Narratives, Things) is encrypted with the same key. This keeps decryption fast — one key unlock per Space, not per node.
- **Asymmetric per Actor:** Each Actor (human or AI) has a public/private key pair. The public key is stored in the graph. The private key **never** enters the graph — it lives in the Actor's sovereign storage (browser wallet for humans, `.keys/` mounted volume for AIs).
- **Keys on Links, Not Nodes:** The Space's symmetric key is not stored on the Space node. It is encrypted with each authorized Actor's public key and stored as a property on the HAS_ACCESS link between that Actor and that Space. No link, no key. Revocation is link deletion.
- **Hierarchical Cascade:** A HAS_ACCESS link to a parent Space grants access to all child Spaces connected via IN links. One key at the root of a Space tree unlocks the entire subtree. Child Spaces may override with their own keys for finer-grained access.
- **Public Content in Plaintext:** Not everything is encrypted. Public Spaces (piazzas, public buildings, open Narratives) store content in plaintext. Encryption applies only to Spaces marked non-public. The physics engine needs plaintext energy/weight values to function — these are always unencrypted.
- **Sovereign Key Storage:** Private keys are never centralized. Humans store them in a wallet-like mechanism (Chrome extension, Mind app, or Solana keypair). AIs store them in `.keys/` directories mounted as volumes when instances launch — generated by mind-mcp per citizen per repository.

## THE CORE INSIGHT

The graph structure is public. The graph content is private.

You can see that Actor A is connected to Space S with energy 0.7 and weight 0.85. You can see that Space S contains 14 Moment nodes. You can see that Actor B also has access. You can trace the entire topology of the universe.

But you cannot read a single word of what those Moments say.

This is the separation that makes one-graph-per-universe safe: the **shape** of relationships is visible (and must be, for physics to work), but the **substance** of those relationships is encrypted. Topology is structure. Content is soul. Structure is public infrastructure. Soul is sovereign.

## COMMON MISUNDERSTANDINGS

- **Not:** Access control. Access control is role-based (owner/admin/member on HAS_ACCESS links) and enforced at the application layer. Space Encryption is **data protection** — even with full database access, content is unreadable without keys.
- **Not:** End-to-end encryption for real-time communication. Voice streams and live WebSocket messages use transport-level encryption (TLS). Space Encryption protects data **at rest** in FalkorDB.
- **Not:** A PKI certificate authority. There is no central authority issuing or revoking certificates. Each Actor generates their own key pair. Trust is established through the graph's existing trust mechanics, not through a certificate chain.
- **Not:** Full-graph encryption. Topology, node existence, link structure, energy values, and weights are **intentionally** plaintext. The physics engine depends on this. Only the `content` and `synthesis` fields of nodes within private Spaces are encrypted.
- **Actually:** A hybrid encryption scheme where symmetric keys protect content for performance, asymmetric keys distribute those symmetric keys via the graph's own link structure, and key revocation is as simple as deleting a link.
